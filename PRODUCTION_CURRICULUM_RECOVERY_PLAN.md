## Executive Summary

Production Begin Learning fails because the active CS1 published package still holds the **pre-certification Studio publication bridge** payload (**7 sections · 117 topics · 0 objectives**, no certification block). Local succeeds because the same subject was later cut over by the **RR-001 operational harness** to a **certified snapshot** package (**5 · 15 · 73**, `authority=certified_snapshot`).

**Critical clarification:** Local “Foundation Version 5” is **not** the fifth sequential CS1 curriculum version. It is `studio_foundation_versions.id = 5` — the **only** CS1 foundation version locally — after four disposable test subjects (`CS1R`/`CS1S`/`CS1U`/`CS1F`) consumed ids 1–4. Production’s CS1 is `id = 1` because it is the only foundation subject on that database. Recovery does **not** require creating four intermediate versions; it requires bringing the **CS1 foundation version row + published package** to the certified payload state local already has.

**Root operational gap:** RR-001 certification + certified catalogue cutover was executed against **local SQLite only**. It was **never executed against production Postgres**. Production stopped after Founder Console Upload → CIP → Preview → Approve → Publish.

**Founder Console alone cannot complete recovery today.** The Console can upload, process (CIP), preview, approve, and publish — but there is **no Console button** that runs Educational Intelligence Generations 1–7 or Founder calibration re-certification. Those steps exist as services/scripts (`WorkspaceGenerationService`, `FounderCalibrationService`, `rr001_verify.py`). On production, the post-CIP `GenerationIntegrationBridge` also left **zero** EI rows (silent failure / empty run), so certification inputs must be regenerated by an operational EI run before Publish can materialise objectives.

**Minimum recovery (no application code changes):** run the RR-001-equivalent EI + calibration + certified publish sequence against the production app/DB (using PDFs already present on production, checksum-identical to local), then verify package structure lengths and Begin Learning derive.

## 1. How local reached the certified CS1 state

### What “Foundation Version 5” actually means

Not: CS1 v1 → v2 → v3 → v4 → v5.  
Yes: first CS1 foundation row received PK **5** because four other subjects were created earlier; that **same row** was later overwritten by RR-001 certified materialisation and republished.

### Exact sequence (Founder + jobs + services + commands)

#### A. Founder Console (initial Studio path — creates foundation row + CIP graph)

1. Create subject / open workspace `ws-cs1` (Subjects hub / Curriculum Studio).
2. Upload **Official CMP** and **Official Syllabus** (document cards).
3. Background CIP jobs (`ProcessingJobService` / `PipelineCoordinator`) run to `ready_for_embeddings`.
4. Founder strip: **Continue to Preview** → inspect hierarchy → **Approve structure** → **Publish**.
5. Services on Publish: `PublicationService.publish` → Management publish → `PublicationBridgeService.publish_to_catalogue` → `CurriculumStudioFoundationService.publish_curriculum`.

This path alone yields a Ready package from **CIP/Foundation structure**, not from a certified EI snapshot. Local evidence shows the CS1 foundation row still carries review notes `Studio publication bridge` even after certification — the **structure JSON** was what RR-001 replaced.

#### B. RR-001 operational harness (transforms structure into certified 5/15/73)

Not a Founder Console button sequence. Command-shaped workflow:

```text
python knowledge/engineering/rr001_release_readiness/rr001_verify.py
```

Internal call chain:

1. **Reconcile** workspace via Studio registry (`get_studio_service().reconcile_workspace`).
2. **Extract/normalize** PDFs from `instance/curriculum_documents/...` (same checksums production now holds).
3. **Optional CMP+syllabus probe** orchestrator (`run_chain` through Gen 7) — regression/confidence proof; not the catalogue binding.
4. **Primary certification:** `WorkspaceGenerationService.run_initial_pipeline(ws-cs1, source_documents=(syllabus,), …)`  
   - Creates/uses chain `ei-chain-ws-cs1`  
   - Persists generations/snapshots/nodes  
   - Gen 7 `DefaultCertificationEngine` → `CERTIFIED_WITH_WARNINGS`  
   - Sets workspace `intelligence_certified=True` + metadata (`ei_certified_snapshot_id`, etc.)
5. **Calibration (local parity):** `FounderCalibrationService.apply` twice (seed balanced, then STRICT_SYLLABUS / CONSOLIDATED / EXAM_FOCUSED) → partial regen Gen 3–7 → re-certify → active snapshot `snap-ae1eaf5e82aabf58`.
6. **Publication cutover:** force checklist facts ready → `PublicationBridgeService.publish_to_catalogue(ws-cs1, actor_id="rr001")`  
   - `StructurePreparationService.structure_dict` dual-reads **certified snapshot**  
   - Writes `parsed_structure_json` on the CS1 foundation version  
   - Approves/publishes Foundation → upserts `published_curriculum_packages`

#### C. Background jobs involved

| Job / worker | Role |
|---|---|
| CIP processing jobs | PDF extract → graph → embeddings readiness (Founder upload path) |
| EI generation store writes | Synchronous in-process during `run_initial_pipeline` / calibration (not a separate Render worker) |
| Publication bridge | Synchronous on Publish / `publish_to_catalogue` |

### Exact missing operational step

**There is no Founder Console control that:**

**Missing step:** an **operational EI certification run** against production (equivalent to RR-001 stages `syllabus_g1_g7` + preferred `calibration_recert`), **then** Founder **Publish** (or bridge `publish_to_catalogue`) so dual-read materialises objectives into the student package.

Without that step, pressing **Publish** again would either:

- **block** on `Publication requires a certified curriculum snapshot` (current gate), or  
- if forced via legacy fallback, re-publish **0 objectives**.
