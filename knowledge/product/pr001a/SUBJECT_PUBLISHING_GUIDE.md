# Subject Publishing Guide

**Programme:** PR-001A  
**Goal:** Publish one subject end-to-end with a clean version trail  

---

## Publishing contract

A subject is ready for students only when:

1. Subject exists.
2. Workspace has CMP + syllabus references recorded.
3. Validation passed (no blocking findings).
4. Preview reviewed and curriculum approved.
5. Version label assigned.
6. Publish succeeds.

Draft and in-progress workspaces are **not** student-visible.

## Recommended sequence

| Order | Action | Done when |
|---|---|---|
| 1 | Create subject | Success flash; code known |
| 2 | Open workspace | Workspace page loads |
| 3 | Assign version | Label visible on workspace |
| 4 | Upload CMP + syllabus | Sources success flash |
| 5 | Validate | Validation completed successfully |
| 6 | Preview | Preview ready |
| 7 | Approve | Approved success flash |
| 8 | Publish | Published success flash |
| 9 | Verify | Dashboard published count / history shows version |

## Version labelling

| Practice | Why |
|---|---|
| Use calendar or semantic labels (`2027.1`, `1.0.0`) | Readable for operators |
| New label for material syllabus changes | Immutable history |
| Never reuse a published label | Avoids version conflicts |

## Subject management

- Continue drafts from the Studio workspace list.
- Prefer advancing the existing workspace rather than creating parallel ones for the same code.
- Archive/rollback beyond this guide is a platform-support operation if something published incorrectly — see [Troubleshooting Guide](TROUBLESHOOTING_GUIDE.md).

## Quality bar before publish

Ask:

1. Are CMP and syllabus references correct for this exam diet?
2. Did validation pass without blocking findings?
3. Does the preview match the official syllabus order you expect?
4. Is the version label unique and meaningful?

If any answer is no, do not publish.
