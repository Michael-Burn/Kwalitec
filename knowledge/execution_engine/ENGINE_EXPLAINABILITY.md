## 1. Purpose

An expert IFoA tutor who cannot say *what was applied* to a script — which rules ran, which limits were checked, which results were recorded, which progress points were reached, and which hard stops remained intact — is not coaching; they are performing.

After Programmes VI–IX have made meaning, ownership, tips, context, contracts, evidence, runtime, conformance, verification, compliance, certification, and evolution speech speakable, and after Workstream 1 has made preparation speech speakable, Programme X still needs one execution-speech answer:

> **“Which constitutional rules were executed, which constraints were evaluated, which execution outcomes were produced, which execution state transitions occurred, and which constitutional boundaries remained intact?”**

That answer must cover every material engine run without inventing educational meaning, transferring authority, minting tips, inventing state, rewriting specifications, freezing a stack as law, inventing unpublished CEE components, determining compliance, certifying implementations, or presenting execution completeness as educational quality or governance outcome.

## 2. What Engine Explainability Is

**Constitutional Execution Engine Explainability** is the constitutional obligation to narrate **lawful constitutional rule execution under published CEE components** — not to invent a second tutor voice from ambient product logs, and not to grade the student or mint constitutional governance dispositions.

| Concept | Definition | Primary question |
|---------|------------|------------------|
| **Constitutional rules executed** | Named published rule identities applied under CEE-01 / CEE-02 | Which constitutional rules were executed? |
| **Constraints evaluated** | Named hard limits assessed under CEE-03 | Which constraints were evaluated? |
| **Execution outcomes produced** | Reconstructable results collected / published under CEE-04 / CEE-07 | Which execution outcomes were produced? |
| **Execution state transitions** | Speakable engine progress recorded under CEE-05 | Which execution state transitions occurred? |
| **Boundaries remaining intact** | Explicit confirmation that forbidden interpretation / amendment / governance / substitution did not occur | Which constitutional boundaries remained intact? |

Engine Explainability is:

- **execution-centred** — it narrates what was executed against completed context, not what preparation assembled;
- **catalogue-bound** — every justification cites published CEE identities;
- **corpus-bound** — every justification cites published specifications and rule identities;
- **non-legislative** — explanation never becomes a back door to amend corpora;
- **non-interpretive** — explanation never smuggles independent interpretation outcomes into “execution notes”;
- **non-governance** — explanation never presents execution completeness as conformance, verification, compliance, or certification;
- **quality-honest** — execution completeness is never narrated as mastery, readiness, or educational quality;
- **technology-honest** — explanation never presents a stack preference as constitutional law;
- **audience-aware** — student speech and developer/auditor traces differ in vocabulary, not in truth;
- **layer-honest** — it does not replace Programme VI tip warrant speech, Programme VII ownership / workflow / state speech, Programme VIII contract / evidence speech, Programme IX judgement speech, or WS1 preparation speech;
- **repeatability-honest** — explanations must not paper over race-dependent or anonymous ambient execution.

Engine Explainability is **not**:

- a rewrite of Constitution / EIP / Programme VI–IX / WS1 meaning;
- a quality report on learning, coaching, or exam readiness;
- a substitute for Programme VIII runtime explainability or Programme IX judgement explainability corpora;
- a substitute for WS1 CECXEQ / CECREQ / CECCQ preparation speech;
- a rendering system, UI template, CI badge, log shipper, or analytics dashboard;
- a claim that clear execution speech guarantees learning, a pass, conformity, compliance, or certification;
- a licence to present pipeline greens, stack traces, or Twin narratives as constitutional proof.

## 3. Mandatory Explanation Questions

Every material constitutional execution should answer all five questions:

### CEEEQ-01 — Which constitutional rules were executed?

Name the primary published Constitution / EIP / Programme VI / VII / VIII / IX rule identities applied under CEE-01 and CEE-02 (paths, catalogue identities, and clauses as applicable). Distinguish *rules dispatched* from *rules applied* when material. Unpublished tribal norms and “how main works” are not constitutional rules. Lawful refuse must name which required rules could not be executed without invention.

### CEEEQ-02 — Which constraints were evaluated?

Name the primary hard limits assessed under CEE-03 — including completed-context constraints (CECX-07 lineage) and engine boundary constraints from [`ENGINE_BOUNDARIES.md`](ENGINE_BOUNDARIES.md). Distinguish *constraint evaluated* from *constraint waived* (waivers are unlawful). Record held / would-be-violated statuses reconstructably. Absence of required constraint evaluation for a material run is a defect.

### CEEEQ-03 — Which execution outcomes were produced?

Name the reconstructable execution outcomes collected under CEE-04 and published under CEE-07. Distinguish *execution outcomes* from *governance dispositions* (CC / CV / CCM / CRT / CEG) and from educational quality claims. Honest incomplete / refused / exception-stopped outcome sets must be speakable. Downstream decision architecture consumes these outcomes; explanation must not upgrade them into seals.

### CEEEQ-04 — Which execution state transitions occurred?

Name the primary CEE-05 transitions for the execution identity (for example dispatched → executing → constraints evaluated → outcomes collected → published / refused / exception-stopped). Distinguish *engine execution state* from *educational state* (EIP-001) and from Programme IX dispositions. Missing transition history for a material run is a defect. Continuity (EIP-005) forbids silent erasure of lawful transition history.

### CEEEQ-05 — Which constitutional boundaries remained intact?

Explicitly confirm that forbidden acts did not occur: no independent interpretation, no redefinition of constitutional meaning, no amendment of specifications, no EIP replacement, no compliance determination, no certification, no governance-outcome authorship, no authority substitution, no stack freeze, no context invention, no constraint waiver. When an exception stopped the run (CEE-06), name the boundary that was preserved by stopping.

## 4. Audience Discipline

| Audience | Vocabulary may… | Truth must… |
|----------|------------------|-------------|
| **Student** | Use plain coaching language | Still name that published rules were applied (or lawfully refused) without claiming mastery or certification |
| **Developer** | Cite CEE IDs, rule paths, component traces | Match student truth; add reconstructable technical identifiers |
| **Auditor** | Require full rule / constraint / outcome / state / boundary map | Reconstruct the run from published inputs without ambient product folklore |

Different vocabulary is lawful. Different constitutional truth is not.

## 6. Defects in Explanation

The following are constitutional explanation defects:

1. Naming stack logs, CI greens, or Twin narratives instead of published rule identities.
2. Claiming compliance or certification from CEEEQ-03 outcomes.
3. Omitting CEEEQ-05 after a material run (including refuses).
4. Presenting different truths to students and auditors.
5. Erasing CEEEQ-04 transition history after the fact.
6. Inventing unpublished CEE components in narration.
7. Soft-amending specifications inside “explanation notes.”
8. Treating missing explanation as optional for material runs.
