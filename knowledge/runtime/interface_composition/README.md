## Purpose

This folder defines **how constitutional runtime interfaces may work together without becoming a single constitutional interface**.

It answers *what composition must optimise*, *which recognised composition patterns exist*, *what composing interfaces may and must never do*, and *how composition is constitutionally explained* — without implementing Runtime A, inventing educational meaning, merging interface identities, transferring constitutional responsibilities, or elevating a transport technology into a constitutional authority.

It does **not** implement REST APIs, GraphQL, gRPC, HTTP, WebSockets, SDKs, authentication, networking, framework code, or Runtime A.

> **Runtime interface composition coordinates constitutional interaction.  
> It never merges constitutional interface identities or transfers constitutional responsibilities.**

## Namespace note

**RIC-01…RIC-07** in this corpus means **Runtime Interface Composition** patterns.  
They are distinct from Runtime Interface categories (**RI-01…RI-07**) under [`../interfaces/`](../interfaces/), Runtime Service Collaboration patterns (**RSC-***) under [`../service_collaboration/`](../service_collaboration/), Runtime Contracts (**RC-***), and Recovery identifiers elsewhere. Context and path always disambiguate: `knowledge/runtime/interface_composition/`.

**Composition vs collaboration.** Interface composition (this corpus) coordinates *interaction contracts* (RI). Service collaboration (WS3 / MS002) coordinates *execution capabilities* (RS). Neither merges identities or transfers constitutional responsibilities. Composing RI-04 may *expose* RSC patterns; it does not redefine them.
