## 1. Purpose

An expert IFoA tutor who cannot say *why* a study action happened — which rule authorised it, what evidence was used, and what limits were preserved — is not coaching; they are performing.

After Programmes VI and VII have made meaning, ownership, tips, and context speakable, Programme VIII still needs one execution-speech answer:

> **“What did runtime do, under which constitutional contract, and why was that lawful?”**

That answer must cover every material runtime action without inventing educational meaning, transferring authority, minting tips, inventing state, or rewriting evidence.

---

## 2. What Runtime Contract Explainability Is

**Runtime Contract Explainability** is the constitutional obligation to narrate **execution of published law** — not to invent a second tutor voice.

| Concept | Definition | Primary question |
|---------|------------|------------------|
| **Contract executed** | Named RC-01…RC-07 binding(s) for the act | Which constitutional contract was executed? |
| **Authorising corpus** | Constitution / EIP / Programme VI / Programme VII artefact(s) that published the rule | Which constitutional corpus authorised it? |
| **Evidence consumed** | Educational Evidence / warrants / published conditions actually used | Which constitutional evidence was consumed? |
| **Outputs produced** | Published events, surfaced recommendations, applied context postures, audit records | Which constitutional outputs were produced? |
| **Boundaries preserved** | Explicit confirmation that forbidden redefinitions / inventions / bypasses did not occur | Which constitutional boundaries were preserved? |

Runtime Contract Explainability is:

- **execution-centred** — it narrates what software did under law;
- **corpus-bound** — every justification cites published producers;
- **audience-aware** — student speech and developer/auditor traces differ in vocabulary, not in truth;
- **layer-honest** — it does not replace Programme VI tip warrant speech or Programme VII ownership / workflow / state speech;
- **non-inventive** — explanation never becomes a back door to mint meaning, tips, or mastery;
- **audit-aligned** — explanation components match RC-07 reconstruction needs.

Runtime Contract Explainability is **not**:

- a rewrite of Programme VI educational meaning explainability;
- a substitute for workflow, authority, recommendation, or state explainability corpora;
- a rendering system, UI template, log shipper, or analytics dashboard;
- a claim that clear execution speech guarantees learning or a pass;
- a licence to present scores or optimiser confidence as constitutional proof.

## 3. Mandatory Explanation Questions

Every material runtime action should answer all five questions:

### RCEQ-01 — Which constitutional contract was executed?

Name the primary RC-01…RC-07 contract(s). Cross-cutting acts name all bound contracts (for example RC-03 + RC-05 + RC-07).

### RCEQ-02 — Which constitutional corpus authorised it?

Cite the Constitution / EIP / Programme VI / Programme VII artefact(s) that published the rule. “Product preference,” “model confidence,” or “similar users” are not constitutional corpora.

### RCEQ-03 — Which constitutional evidence was consumed?

Distinguish:

- EIP-002 Educational Evidence of understanding (when actually used);
- Programme VI warrants / artefacts;
- Programme VII orchestration, ownership, recommendation, or context facts;
- published condition evaluations.

Never present coverage, time, engagement, or Twin estimates as understanding evidence unless the Evidence Model permits that classification.

### RCEQ-04 — Which constitutional outputs were produced?

Name only published output classes: workflow events, authority dispositions, recommendation artefacts / sets, EST/CST postures, audit records, or explicit refuse/defer/escalate outcomes.

### RCEQ-05 — Which constitutional boundaries were preserved?

Confirm the hard stops in `CONTRACT_BOUNDARIES.md` that were checked — especially non-redefinition of meaning, authority, evidence, tips, state, workflow, and specifications.

| ID | Component | Obligation |
|----|-----------|------------|
| **RCEC-01** | Contract identity | Named RC-01…RC-07 binding(s) |
| **RCEC-02** | Authorising corpus refs | Documented constitutional producers |
| **RCEC-03** | Evidence / warrant refs | What was consumed, with claim-class honesty |
| **RCEC-04** | Output catalogue | What published artefacts / events / postures resulted |
| **RCEC-05** | Boundary preservation record | Confirmation that forbidden acts did not occur |
| **RCEC-06** | Refusal / deferral honesty | When no lawful execution existed, say so |
| **RCEC-07** | Continuity note | Prior lawful history not erased (EIP-005) |
| **RCEC-08** | Non-claim honesty | Explicit refusal of mastery / pass / meaning-rewrite overclaim |
| **RCEC-09** | Audience projection | Student-plain vs developer/auditor vocabulary over one truth |
| **RCEC-10** | Provenance integrity | Constitutional refs survived packaging into speech / audit |

Components are **constitutional content obligations**, not database columns, API fields, or UI widgets. Persistence and rendering are out of scope for MS001.

---

## 5. Audience Rules

| Audience | May hear | Must not hear as educational law |
|----------|----------|----------------------------------|
| **Student** | What happened next, why it was allowed, what evidence supported it, and what limits apply — in plain educational language | Internal RC IDs as theatre; stack traces; optimiser scores as “proof you are ready” |
| **Developer / auditor** | Full RCEQ-01…05 answers, corpus paths, contract IDs, boundary checks, provenance | Product success metrics substituted for constitutional refs |

Student and developer traces must describe the **same constitutional truth**. Vocabulary may differ; facts may not.

## 6. Layering with Upstream Explainability

| Layer | Corpus job | Runtime speech role |
|-------------------|---------------------|
| Programme VI coach / planner explainability | Why educational guidance is warranted | Consume; do not rewrite |
| Programme VII workflow explainability | How orchestration flowed | Narrate execution of WS1 under RC-03 |
| Programme VII authority explainability | Why a component was permitted to decide | Narrate consumption under RC-04 |
| Programme VII recommendation explainability | Why a tip / set is speakable | Narrate consumption under RC-05 |
| Programme VII state explainability | Why context is live / how it succeeded | Narrate consumption under RC-06 |
| **Programme VIII contract explainability** | **Which runtime contract executed under which law** | **This document** |

A complete material journey may carry every layer that applied. Runtime speech without upstream warrant is hollow. Upstream warrant without runtime contract identity invites silent reimplementation drift.
