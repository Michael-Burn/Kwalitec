## 1. Purpose

An expert IFoA tutor who cannot say *which API was used*, *which interface was exposed*, *what was requested*, and *what lawful response returned* is not coaching; they are performing.

After Programmes VI–VII and Programme VIII WS1–WS4 have made meaning, ownership, tips, context, contracts, evidence, services, and interfaces speakable, Programme VIII WS5 still needs one exposure-speech answer:

> **“What constitutional API was used, which runtime interface did it expose, what was exchanged, and which boundaries were preserved?”**

That answer must cover every material API interaction without inventing educational meaning, transferring authority, minting tips, inventing state, altering evidence, redefining interfaces, or elevating transports into law.

---

## 2. What Runtime API Explainability Is

**Runtime API Explainability** is the constitutional obligation to narrate **exposure under published law** — not to invent a second tutor voice or a protocol story that substitutes for constitutional producers.

| Concept | Definition | Primary question |
|---------|------------|------------------|
| **API used** | Named RA-01…RA-07 binding(s) for the interaction | Which constitutional API was used? |
| **Interface exposed** | Published RI-01…RI-07 interaction contract surfaced through the API | Which runtime interface did it expose? |
| **Request received** | Authorised constitutional request shape actually accepted | Which constitutional request was received? |
| **Response returned** | Authorised constitutional disposition / artefact / audit / diagnostic record returned | Which constitutional response was returned? |
| **Boundaries preserved** | Explicit confirmation that forbidden redefinitions / exposures / bypasses / mutations did not occur | Which constitutional boundaries were preserved? |

Runtime API Explainability is:

- **exposure-centred** — it narrates which interface was exposed and what was exchanged under law;
- **interface-bound** — every justification cites published RI contracts, not wire methods;
- **audience-aware** — student speech and developer/auditor traces differ in vocabulary, not in truth;
- **layer-honest** — it does not replace Programme VI tip warrant speech, Programme VII ownership / workflow / state speech, or Programme VIII contract / evidence / service / interface speech;
- **non-inventive** — explanation never becomes a back door to mint meaning, tips, mastery, policy, or interface redefinition;
- **technology-neutral** — protocol names may appear as ops breadcrumbs, never as constitutional warrant;
- **audit-aligned** — explanation components match RA-06 reconstruction needs.

Runtime API Explainability is **not**:

- a rewrite of Programme VI educational meaning explainability;
- a substitute for contract, evidence, service, interface, workflow, authority, recommendation, or state explainability corpora;
- a rendering system, UI template, OpenAPI description, log shipper, or analytics dashboard;
- a claim that clear exposure speech guarantees learning or a pass;
- a licence to present scores, latency, or optimiser confidence as constitutional proof.

## 3. Mandatory Explanation Questions

Every material API interaction should answer all five questions:

### RAEQ-01 — Which constitutional API was used?

Name the primary RA-01…RA-07 API(s). Cross-cutting interactions name all bound APIs (for example RA-05 + RA-06).

### RAEQ-02 — Which runtime interface did it expose?

Cite the published RI-01…RI-07 interaction contract(s) the API surfaced. “This REST route,” “this gRPC method,” or “this OpenAPI operation” are not constitutional interfaces.

### RAEQ-03 — Which constitutional request was received?

Distinguish:

- Bound RI exposure intent and published request shapes;
- RC bindings and published condition evaluations;
- EIP-002 / WS2 evidence artefacts (when actually used);
- Published CE-class events;
- Programme VI warrants / Programme VII orchestration artefacts;
- Explicit refuse / diagnostic scopes for non-executing interactions.

Never present coverage, time, engagement, or Twin estimates as understanding evidence unless the Evidence Model permits that classification.

### RAEQ-04 — Which constitutional response was returned?

Name only published response classes: dispositions, workflow events, recommendation artefacts / sets, EST/CST postures, audit records, diagnostic reports, or explicit refuse/defer/escalate outcomes.

### RAEQ-05 — Which constitutional boundaries were preserved?

Confirm the hard stops in `API_BOUNDARIES.md` that were checked — especially non-redefinition of interface contracts, non-exposure of internals as law, non-bypass of contracts, and non-modification of specifications.

## 5. Audience Rules

| Audience | May hear | Must not hear as educational law |
|----------|----------|----------------------------------|
| **Student** | What was requested next, why it was allowed, what came back, and what limits apply — in plain educational language | Internal RA / RI IDs as theatre; stack traces; protocol status codes as “proof you are ready” |
| **Developer / auditor** | Full RAEQ-01…05 answers, interface paths, API IDs, boundary checks, provenance | Product success metrics or transport details substituted for constitutional refs |

Student and developer traces must describe the **same constitutional truth**. Vocabulary may differ; facts may not.

| Programme VIII service explainability | Which service capability ran under which law | Narrate exposure under RA-04 / specialised RAs |
| Programme VIII interface explainability | Which interaction contract exposed which capability and exchanged what | Narrate that the API exposed that interface without redefining it |
| **Programme VIII API explainability** | **Which exposure contract exposed which interface and exchanged what** | **This document** |

A complete material journey may carry every layer that applied. API speech without upstream warrant is hollow. Upstream warrant without API identity invites silent reimplementation drift behind transports.
