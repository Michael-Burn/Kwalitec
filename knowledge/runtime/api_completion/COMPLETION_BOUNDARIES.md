## 1. Purpose

Runtime that silently turns “API composition finished” into “student succeeded,” “interface composition completed,” “collaboration completed,” “execution completed,” “workflow closed,” “identities merged,” “interfaces redefined,” or “the Constitution now says X” destroys student trust and educational integrity.

This document draws a bright line between **lawful API-composition-completion confirmation** (Programme VIII / WS5 / MS003) and **educational / interface-composition / collaboration / execution / orchestration / authorship / identity-merger / interface-redefinition judgements** owned elsewhere.

---

## 2. Boundary Principles

1. **Confirm composition, do not author meaning.** Completion affirms fulfilment of published API coordination duties; it does not create educational truth.
2. **Composition only.** Learning, mastery, and progress are never inferred from close.
3. **Not interface composition completion.** Programme VIII / WS4 / MS003 owns interface-composition fulfilment.
4. **Not service collaboration completion.** Programme VIII / WS3 / MS003 owns collaboration fulfilment.
5. **Not execution completion.** Programme VIII / WS1 / MS003 owns execution-cycle fulfilment.
6. **Not workflow completion.** Programme VII owns orchestration fulfilment.
7. **Not identity merger.** MS001 owns the API catalogue; close never merges or redefines it.
8. **Not interface redefinition.** WS4 owns Runtime Interface meanings; close never invents or rewrites them.
9. **Published criteria only.** REST, GraphQL, gRPC, HTTP, OpenAPI, SDKs, and gateway exits are not fulfilment law.
10. **Published records only.** Composition audit continuity is constitutional, not free-form tracing theatre.
11. **Reference participants, patterns, and interfaces honestly.** Named RA APIs, RAC patterns, and exposed RI contracts may be cited; MS001 / MS002 / WS4 law is not rewritten by citing them.
12. **Meaning non-reinterpretation.** Programme VI questions survive close intact.
13. **Evidence non-reinterpretation.** Classifications stay with the Evidence Model.
14. **State non-invention.** Context postures stay with Programme VII EST/CST law.
15. **Recommendation non-invention.** Tips stay with Programme VII / VI owners.
16. **Determinism.** Race-dependent composition completion is a defect.
17. **Implementation independence.** Protocols, gateways, and OpenAPI documents never become constitutional furniture.
18. **Explain the stop.** Students and developers should hear when close must be refused.
19. **No emergency exemption.** Load, deadlines, and demos never mint composition-completion power.

## 3. What Runtime API Composition Completion May Do (Lawful)

| Lawful action | Constitutional meaning |
|---------------|------------------------|
| **Confirm composition fulfilment** | Affirm RACC-01…RACC-05 when published criteria hold for a lawful composition |
| **Reference participating APIs** | Cite RA-01…RA-07 participants and composition roles under MS001 / MS002 — without merging or redefining the RA catalogue |
| **Reference composition patterns** | Cite RAC-01…RAC-07 pattern(s) whose published steps finished or lawfully stopped — without inventing unpublished gateways |
| **Reference Runtime Interfaces** | Cite RI-01…RI-07 contracts exposed through participating APIs — without redefining, absorbing, or inventing interfaces |
| **Preserve audit continuity** | Keep reconstructable RA-06 / RAC / RC-07 trails intact across retries, replacements, and redeploys (EIP-005) |
| **Refuse unlawful close** | Prefer honest not-yet / refuse-close over improvisation, merger, or interface-redefinition theatre |
| **Remain deterministic** | Same published inputs → same completion judgement class |
| **Remain replaceable** | Honour completion law in any compliant implementation |
| **Explain completion** | Answer participants / patterns / interfaces / requests / responses / boundaries without rewriting meaning |

These actions **confirm**. They do **not** publish a new Constitution, invent coach questions, mint tips, author ownership maps, certify mastery, affirm RICC/REC/ECC/RSCC by declaration, close Programme VII workflows, merge RA identities, or redefine Runtime Interfaces.

## 4. What Runtime API Composition Completion Must NEVER Do

| Forbidden action | Why | Lawful alternative |
|------------------|-----|--------------------|
| **Merge API identities** | MS001 owns the RA catalogue; MS002 forbids merger by composition | Keep each participant’s MS001 identity and exposures intact |
| **Redefine Runtime Interfaces** | WS4 owns RI meanings; close does not invent or rewrite them | Consume published RI contracts; escalate for corpus amendment |
| **Imply interface composition completion** | Programme VIII / WS4 / MS003 owns RICC fulfilment | Affirm API composition completion only; require RICC corpus for interface-composition close |
| **Imply service collaboration completion** | Programme VIII / WS3 / MS003 owns RSCC fulfilment | Affirm API composition completion only; require RSCC corpus for collaboration close |
| **Imply execution completion** | Programme VIII / WS1 / MS003 owns REC fulfilment | Affirm API composition completion only; require REC corpus for execution-cycle close |
| **Imply workflow completion** | Programme VII WS1 / MS003 owns orchestration fulfilment | Affirm API composition completion only; require Programme VII corpus for workflow close |
| **Imply educational success** | Educational success is not a composition property | Say composition responsibilities are fulfilled; remain silent on mastery / progress / pass |
| **Modify constitutional specifications** | Constitution / EIP / Programmes VI–VIII are amended only under their governance | Change code to obey law, or propose a corpus amendment — never patch law in a composition-completion handler |
| **Imply Programme VI educational completion** | Coach / planner completion models own educational fulfilment where defined | Keep educational completion judgements with Programme VI |
| **Imply Evidence Consumption Completion** | WS2 / MS003 owns ECC fulfilment | Affirm API composition completion only; require ECC corpus for evidence-handling close |
| **Redefine MS001 / MS002 meanings at close** | API and composition law are not rewritten by “done” | Consume published catalogues; escalate for corpus amendment |
| **Invent tips / state / evidence classes at close** | Programme VII / VI / EIP-002 writers own those artefacts | Surface only already-authorised composition responses or none |
| **Treat REST / GraphQL / gRPC / HTTP / OpenAPI / SDK / gateway exits as fulfilment** | Operational proxies are not completion law | Evaluate RACC-01…RACC-05 |
| **Treat Twin / Adaptive / UI done-flags as publishers of completion law** | They are consumers / delivery surfaces | Require published criteria or refuse |
| **Become irreplaceable by composition topology** | RACCO-04 replaceability | Keep completion law implementation-independent |
| **Erase continuity to force a clean close** | EIP-005 | Preserve history; re-enter at published points |

## 6. Boundary Checks (Pre-Affirmation)

Before a material composition completion is affirmed, confirmation requires affirmative answers:

| Check | Question |
|-------|----------|
| **ACCB-01 Composition lawfulness** | Did a published MS001 / MS002 composition exist (not completion theatre for never-started coordination)? |
| **ACCB-02 Criteria** | Do RACC-01…RACC-05 hold? |
| **ACCB-03 Identity non-merger** | Does affirmation avoid merging or absorbing MS001 API identities? |
| **ACCB-04 Interface non-redefinition** | Does affirmation avoid redefining Runtime Interfaces? |
| **ACCB-05 Interface-composition non-claim** | Does affirmation avoid implying interface composition completion or RICC completion? |
| **ACCB-06 Collaboration non-claim** | Does affirmation avoid implying service collaboration completion or RSCC completion? |
| **ACCB-07 Execution non-claim** | Does affirmation avoid implying execution completion or REC completion? |
| **ACCB-08 Learner-success non-claim** | Does affirmation avoid implying learner success, progress, mastery, or pass? |
| **ACCB-09 Workflow non-claim** | Does affirmation avoid implying Programme VII workflow completion? |
| **ACCB-10 Spec immutability** | Does affirmation avoid modifying constitutional specifications? |
| **ACCB-11 Participant honesty** | Are references limited to published RA participants without inventing mega-APIs? |
| **ACCB-12 Pattern honesty** | Are pattern references limited to published RAC-01…RAC-07 identities? |
| **ACCB-13 Interface honesty** | Are exposed-interface references limited to published RI-01…RI-07 identities without redefinition? |
| **ACCB-14 Response honesty** | Are produced responses limited to published constitutional classes without reinterpretation? |
| **ACCB-15 Record honesty** | Do composition records support the judgement without substituting protocol / gateway / OpenAPI theatre? |
| **ACCB-16 Continuity** | Is audit continuity preserved (EIP-005)? |
| **ACCB-17 Determinism** | Is the judgement reproducible from published inputs? |
| **ACCB-18 Explainability** | Can RACCAQ questions in `COMPLETION_EXPLAINABILITY.md` be answered honestly? |

Any failed check → not yet / refuse close. Do not “best-effort” invent fulfilment.
